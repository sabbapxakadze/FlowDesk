# 0049 - Settings for the first deploy: a Render blueprint, a careful database pool, uploads switched off

Status: Accepted - 2026-10-08. Phase 9 slice 9.4 (the code half). Builds on ADR 0045 (hosting on Render free + Neon) and ADR 0046 (production server).

## Context

The first deploy puts the one-process server (ADR 0046) on a free Render web service with a free Neon Postgres. Four things in the code did not yet fit that place:

1. Render's free disk is wiped on every restart and sleep, so an uploaded file would be accepted and then silently vanish.
2. Neon suspends its compute after minutes of quiet and then closes idle connections. A `pg` pool that has no `error` listener turns such a closed connection into an uncaught exception, which stops the whole server.
3. The service's own address (`APP_URL`) is only known once the service exists, which made the first deploy a two-step dance.
4. Neon's free plan has a limited number of connections, and the pool had no upper bound set.

## Decision

- **`render.yaml`** (a Blueprint at the repository root): one `web` service, Node runtime, free plan, Frankfurt (near the Neon database, also Frankfurt), health check `/api/health` (does not touch the database). Build: `corepack enable && pnpm install --frozen-lockfile && pnpm build`. Start: `NODE_ENV=production node apps/api/dist/index.js` (`NODE_ENV` is set in the start command only, so the install still gets the build tools). Fixed settings: `NODE_VERSION=24`, `SERVE_WEB`, `RUN_MIGRATIONS`, `TRUST_PROXY=1`, `DEMO_ENABLED=true`, `STORAGE_DRIVER=disabled`. Asked for once at creation (`sync: false`): `DATABASE_URL` (the Neon direct string) and `RESEND_API_KEY` (a placeholder). Generated by Render (`generateValue`): `JWT_SECRET`, `ATTACHMENT_SIGNING_SECRET`.
- **`APP_URL` falls back to `RENDER_EXTERNAL_URL`** (`parseEnv` in `config/env.ts`): a set, non-empty `APP_URL` always wins (a custom domain later); with neither, the server still refuses to start.
- **`STORAGE_DRIVER`** (`local` default, or `disabled`): with `disabled` an upload is refused up front with a 503 `uploads_disabled` ("File uploads are switched off on this deployment."), before any image processing or database change (`assertUploadsEnabled()`, called at the start of an attachment upload and a photo upload, and inside `saveFile` as the single door). The real object storage (R2 or similar) replaces this in slice 9.5.
- **The pool** (`db/client.ts`): `max` from `DB_POOL_MAX` (default 10), idle connections closed by us after 30 s, a 15 s connect timeout (a suspended Neon database needs a moment to wake), and a **`pool.on("error")` listener that logs and drops the dead connection**.
- **TLS** comes from the connection string (Neon's string carries `sslmode=require`); nothing is hard-coded.

## Tested

API tests: the upload refusal through the real HTTP routes (attachment: refused, nothing stored, the list stays empty; photo: refused, no file, no database change) and at the storage door; the pool has an error listener and survives an emitted idle-connection error; the pool is capped; `parseEnv` (the fallback, an explicit value winning, an empty value counting as unset, a missing address still failing, the defaults). Mutation checks: removing the pool listener, the storage switch and the `RENDER_EXTERNAL_URL` fallback were each caught.

## Trade-offs and limits, named

- With uploads off, **the upload buttons still show** and the refusal appears when someone tries. Hiding them needs the web app to learn the setting; it comes with real storage (9.5).
- **Emails fail quietly** with the placeholder key, so password reset and invitations do not work until a domain exists (ADR 0045).
- `DEMO_ENABLED=true` makes "Try the demo" a public write endpoint (capped, rate limited, copies deleted after 2 hours: ADR 0044). It is one line in `render.yaml`.
- `generateValue`'s length was not checked in the docs; the server refuses to start with a secret shorter than 32 characters, with a clear message, so a short one would show on the first deploy.
- Auto deploy on every push to the linked branch is Render's default; deploying only after CI is green is a later option (not checked how Render offers it).

## Result of the first deploy (2026-10-08)

The service is live on Render's free plan at `https://flowdesk-yotg.onrender.com` (Frankfurt), database on Neon (Frankfurt, Postgres 18). Build and start took 1 min 15 s on the first deploy; the log shows `database migrations are up to date` (the migrations ran on Neon from empty), Render's health checks answer 200, and the security header already names the service's own address, so `APP_URL` from `RENDER_EXTERNAL_URL` worked. Read-only checks from outside passed (health, landing page and its headers, a deep link, a 404 for a missing file, a JSON 404 for an unknown API route, the demo info). The owner then ran the browser smoke test by hand (Try the demo, board, live update, register, log in): everything worked except email, as designed (placeholder `RESEND_API_KEY`).

**How it was created, honestly:** by hand in the dashboard (New > Web Service), not from `render.yaml`. The Blueprint flow asked for a payment card first (a $1 verification hold was taken; a card ended up saved on the account, which the owner had not expected). Render's own default build command for the repository was pnpm, so `corepack enable` was dropped; `render.yaml` now matches what runs. Free plan on a Hobby workspace; the billing page showed no invoices and a $0.00 balance. The saved card was then removed (Render blocks adding another until 2026-11-01 and says no paid service can be created or restored until then); the service answered its health check 20+ minutes later, so a free service runs without a card. Free services over their limits are suspended, not billed (from Render's free-plan page as I read it; not tested).

## Not verified

Everything about Render itself: that its native build handles this pnpm workspace and `corepack enable`, the build's memory use on 512 MB, how its proxy forwards `X-Forwarded-For`, and how Neon behaves when it wakes. Of the list above, the first deploy settled: the native pnpm build, the connection to Neon (TLS, `channel_binding`), the migrations on Neon and `RENDER_EXTERNAL_URL`. Still open: the build's memory use on 512 MB under a larger bundle, how Render's proxy forwards `X-Forwarded-For` (the rate limits depend on it, `TRUST_PROXY=1`), and what a cold start after sleep and Neon's wake do to the first request.
